# API-контракт как артефакты без живого бэкенда

Шаги 3–6 курса требуют TypeSpec-контракт, генерацию OpenAPI, клиентский SDK
и серверные артефакты — это противоречит ADR-0001 («бэкенда не существует
и не планируется»). Владелец выбрал трактовку: **контракт как артефакты**.

TypeSpec описывает модели и эндпоинты домена (типы события, слоты, записи)
по утверждённой спецификации (`docs/spec/app.md`) — не для живого сервера,
а чтобы сгенерировать из него `docs/openapi.yaml`, строгие типы для
фронтенда (шаг 4) и серверные артефакты (шаг 5). HTTP-контракт обслуживает
мок-сервер рантайма (см. обновление ниже); хранение данных — `localStorage`
(ADR-0001 в силе).

## Обновление (2026-10-22, требование владельца)

Требование курса (шаг 6): «Фронтенд обращается к API через сгенерированный
клиентский SDK». Фронтенд обязан вызывать методы из `src/api/` (hey-api);
руками написанный `fetch` запрещён. Поскольку живого бэкенда нет, на старте
приложения ставится перехватчик глобального `fetch` (`src/lib/mockServer.ts`):
он ловит вызовы SDK и маршрутизирует их в модуль данных `src/lib/bookings.ts`,
который отвечает по контракту — пути операций, статусы 200/400/404/409,
тело ошибки `{ code, message }`. Правила бронирования (конфликты слотов)
проверяются в модуле данных, «на бэкенде», а не в UI. Замена мок-сервера
на живой бэкенд не требует правок компонентов — достаточно убрать
перехватчик и указать реальный `baseUrl`.

## Consequences

- `spec/main.tsp` — исходник контракта, `docs/openapi.yaml` — сгенерированный
  артефакт (коммитится), генерация — `make openapi`.
- Контракт зеркалит внешнее поведение спецификации и служит входом для
  генераторов шагов 4–6; если позже появится живой бэкенд — он реализует
  этот контракт, а не новый.
